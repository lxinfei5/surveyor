# 看清全局：建树与覆盖

本参考展开[主文](../SKILL.md)的第一个方向。

## 先选拆分依据

先写清一个节点在回答什么问题，再拆它的子节点。不要把原因、工具和行动混成同级分支。

例如，“拿不到记录”的原因可按访问链路拆分。来源不存在、入口失败、权限不足属于不同环节。浏览器和连接器则是验证这些环节的实现方式。

| 检查对象 | 要确认的关系 | 常见错误 |
|---|---|---|
| 同一维度的分支 | 是否遗漏或重叠 | 用“其他”隐藏未知情况 |
| 不同维度 | 独立还是有约束 | 把不同类型直接叫作正交 |
| 上下级节点 | 支持、依赖还是必要条件 | 把一个症状当作原因 |
| 替代路线 | 满足任一路线是否足够 | 找到可用工具就宣称达成目标 |
| 组合原因 | 是否需要多个条件共同成立 | 单项无效就删除整个组合 |
| 共享依赖 | 哪个节点保存权威事实 | 在多个分支保存冲突副本 |

如果改变一个维度会限制另一维度，它们就存在依赖。只组合合法情况，不把所有值机械相乘。

## 树、图和分区的边界

问题树记录当前搜索入口与父子关系。现实依赖可以构成图，共享节点通过引用连接。

遇到循环依赖时，标出循环及其验证入口。不要把同一个状态反复展开成“新分支”。

唯一责任方适用于分类、路由和交付责任。它不要求研究假说互斥。两个假说可能分别解释同一现象的不同部分。

## 覆盖检查

1. 用一个正常案例检查主要路径。
2. 用一个边界案例检查分支切换。
3. 用一个失败案例检查证据和语义。
4. 将无法解释的案例记录为结构缺口。
5. 检查是否遗漏未被当前工具支持的情况。

“已知案例均有归属”只能支持当前覆盖范围。它不能证明开放空间绝对完整。

## 控制深度

全局扫描先列主要分支和未解释现象。随后用深度优先验证最关键的路径。

只有会影响根目标或关键判断的分支才继续细分。细分应产生新的区分证据，而不是增加相近标题。

已知分支耗尽而目标未达时，按[扩树规则](depth-first-search.md)重查结构。不要把当前地图的边界当成现实边界。
