# 看清全局：建树与覆盖

本参考展开[主文](../SKILL.md)的第一个方向。

## 先选拆分依据

先写清一个节点在回答什么问题，再拆它的子节点。不要把原因、工具和行动混成同级分支。

例如，“拿不到记录”的原因可按访问链路拆分。来源不存在、入口失败、权限不足属于不同环节。浏览器和连接器则是验证这些环节的实现方式。

| 检查对象 | 要确认的关系 | 常见错误 |
|---|---|---|
| 同一维度的分支 | 是否遗漏或重叠 | 用“其他”隐藏未知情况 |
| 不同维度 | 独立还是有约束 | 把不同类型直接叫作正交 |
| 上下级节点 | 支持、依赖还是必要条件 | 把一个症状当作原因 |
| 替代路线 | 满足任一路线是否足够 | 找到可用工具就宣称达成目标 |
| 组合原因 | 是否需要多个条件共同成立 | 单项无效就删除整个组合 |
| 共享依赖 | 哪个节点保存权威事实 | 在多个分支保存冲突副本 |

如果改变一个维度会限制另一维度，它们就存在依赖。只组合合法情况，不把所有值机械相乘。

## 树、图和分区的边界

问题树记录当前搜索入口与父子关系。现实依赖可以构成图，共享节点通过引用连接。

遇到循环依赖时，标出循环及其验证入口。不要把同一个状态反复展开成“新分支”。

唯一责任方适用于分类、路由和交付责任。它不要求研究假说互斥。两个假说可能分别解释同一现象的不同部分。

协作分支按问题、解释或验证需要划分，模型和工具是执行选择。比较结果时追溯原始来源和观察过程：多名执行者引用同一材料，仍是同源支持；各自新增的分析可保留，但不因此增加独立事实证据。跨分支联系也应连回原节点和适用条件，避免将组合猜想写成各方已经共同证实的结论。

## 覆盖检查

1. 用一个正常案例检查主要路径。
2. 用一个边界案例检查分支切换。
3. 用一个失败案例检查证据和语义。
4. 将无法解释的案例记录为结构缺口。
5. 检查是否遗漏未被当前工具支持的情况。

“已知案例均有归属”只能支持当前覆盖范围。它不能证明开放空间绝对完整。

覆盖还应检查当前项目的表达能力：是否只允许既有模块、既有指标或工具可见的对象成为分支？将被排除的相关案例与规则来源对照，区分真实约束与环境造成的盲区。遇到任务和环境不匹配时，按[环境适配](real-intent.md)提出最小调整；不要用“其他”吞掉这些案例，也不因发现盲区自动取得修改权限。

## 从材料发现问题，回看旧理解

没有现成问题的开放探索，可先以用户关心的对象与已有认识为范围，从未解释的观察、材料间的冲突或可能相通的机制形成候选问题。优先能改变理解或打开验证路径的联系，不为“新颖”堆砌联想；认识基线不清楚时，将其称为候选启发。

反刍是带着变化回看相关旧材料。新事实是否改变旧解释的适用条件？另一主题是否提供了原先缺少的机制？过去暂时无用的片段是否获得了新的连接？优先沿这些关系定向回看，无需每次扫描全部历史。

保留来源和原条件，比较旧理解与现在的差别。重新组合已有事实也可产生新问题，但联系本身仍是推断。若只有措辞或分类变化，应如实说没有形成新判断；不能把旧结论的否定范围随之抹掉。

例如，旧记录显示“成功导出后仍反复重试”，新访谈提到“收件人看不到原链接”，可提出“交付是否还受访问条件影响”。这值得新增分支，但尚不能断定权限就是重试原因。重复操作、链接过期等解释仍需区分。

线索尚不适合归树时，留在现有材料或任务记录中即可；保留触发它的证据和不确定性，不要求每个片段填写节点表。准备投入验证时，再接入能解释其依赖关系的节点。新联系推翻上级前提时及时回查；仅仅有趣的旁支不必打断当前深入。

Agent 可建议优先追问哪些方向，也可在任务范围内排除已被证据否定的假设。取证排序、局部否定与删除用户保留的思想方向是不同决定，不因当前无法验证就替用户裁剪。发现任务外问题不自动取得扩展执行的授权。

## 控制深度

全局扫描先列主要分支和未解释现象。随后用深度优先验证最关键的路径。

只有会影响根目标或关键判断的分支才继续细分。细分应产生新的区分证据，而不是增加相近标题。

已知分支耗尽而目标未达时，按[扩树规则](depth-first-search.md)重查结构。不要把当前地图的边界当成现实边界。
