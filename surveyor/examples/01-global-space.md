# Demo 1：看清取证的全局空间

本例使用虚构输入演示方法。表中观察是教学设定，不代表真实查询结果。

## 输入与目标

用户说：“给我判断这项服务变更是否完成。”

验收已确认：代码已合入，目标环境已部署，指定账户的样本结果符合预期。任何一项未知，都不能宣称整体完成。

## 初始误区

只列“代码平台、浏览器、日志工具”会漏掉数据验证。工具列表无法说明每种证据要证明什么。

先按需要证明的命题建树，再把工具作为实现选择。

```text
R 变更完成？【同时满足】
├─ A 目标代码已合入
│  └─ 目标提交、目标分支和变更内容一致
├─ B 目标环境已部署
│  └─ 运行版本包含目标提交
└─ C 样本结果符合预期
   ├─ C1 账户、环境和时间窗匹配
   └─ C2 权威记录满足验收条件
```

账户访问权限是 C 的依赖。浏览器和连接器可能共享该权限，不能作为两份独立证据。

## 遍历与观察

| 节点 | 教学观察 | 判断 |
|---|---|---|
| A | 目标提交已进入目标分支 | 支持代码合入 |
| B | 运行实例报告的版本包含目标提交 | 支持部署完成 |
| C1 | 测试账户和目标时间窗可确认 | 支持样本范围 |
| C2 | 权威记录查询权限不足 | 受阻，不能支持样本验收 |

A 和 B 均通过，仍不足以支持 R。C 的查询受阻，也不表示样本结果错误。

## 反例与空间修正

| 反例 | 暴露的问题 | 修正 |
|---|---|---|
| 把合并记录同时放在 A 和 B | 同一证据不能证明运行状态 | B 保留运行版本证据 |
| 服务成功日志代替权威记录 | 持久化是否完成仍未知 | 保留 C2 |
| 测试环境样本代替目标环境 | 验收对象改变 | C1 增加环境核对 |
| 用公开摘要代替账户内记录 | 失败路径改变证据等级 | C2 保持受阻状态 |

## 示例交付

“代码合入和部署已确认。样本结果仍待确认，缺少权威记录的查询权限。整体尚未验收。”

## 验收本方向

读者应能为每项验收找到证据归属。读者也应能指出缺口，以及缺口为何影响根结论。

本例不要求继续枚举所有工具。下一步应寻找能满足 C2 的授权路径。

## 延伸：另一项开放探索中的旧材料反刍

用户随后另行要求：“结合近期材料，看看还有哪些值得研究的问题；先不用改系统。”以下仍是虚构教学设定，不改变前一项验收结论。

旧材料记录：五次“导出成功后重试”被暂记为用户误操作。新增访谈中，两位收件人表示原链接无法打开；另一位用户表示重复点击是为了核对版本。

这组材料让原先只覆盖“生成成功”的理解出现缺口：交付后的访问条件和版本辨识可能影响重复操作。可以主动提出新问题：“用户能否取得并辨认自己需要的那一版结果？”无需等到旧问题树耗尽才发现它。

有价值的反刍是重新解释旧重试记录，不能把两次访谈推广为五次重试的统一原因。下一项区分证据可以是同一交付对象、身份、版本和时间窗下的访问结果；若权限正常却仍重试，则保留版本辨识或其他解释。无法把新访谈与旧记录对应时，也要保留这个缺口。

本次可交付有依据的新问题及竞争解释，建议哪些值得先看，保留用户尚未裁剪的方向。它不证明产品已修复，也不授权修改权限。若本次仍只要求判断原变更是否完成，则该联系最多作为旁支线索，C2 仍需原来的权威验收证据。
